## Growth — the embed invites a creator's readers to post, and every invitation was dead

The previous run proved the embed's freshness poll 404'd (patch 0e). This run pointed the same lens
— *test the promise the shared artifact makes* — at what the embed asks a reader to **do**.

**The finding.** The embed renders three invitations, in a creator's readers' faces, on the
creator's own page:

- a dashed reader-zone card: **"+ Your theory goes here — be the first, tap to post"**
- a second: **"? Or just ask something — no theory required"**
- on every opened card: **"Start the discussion"**

The composer dialog and its script **are not shipped to the embed at all** — `#gbc-post` is absent
and `window.gbCompose` is `undefined` there. The `data-compose` click handler lives inside that
same unshipped script, so there was no handler to fire.

Tapping any of them did **nothing**. Not an error — *nothing*. Zero console output, zero page
errors, no visual response. Verified in real Chromium with `localhost:8909` framing
`127.0.0.1:8908`, so genuinely cross-origin. A creator would never learn this had happened, and
neither would we: it is silent on both sides of the frame. Worse than the poll bug, which at least
logged a 404.

**Fix, and it is a growth fix rather than only a repair.** In an embed those invitations become
links to the full board — `target="_blank"`, `rel="noopener"`, deep-linked
(`#card=<id>&post=comment`) so the reader lands on the card they were reading with the composer
already open. A dead tap becomes a referred visit. That is what the embed is *for*: it should send
a creator's readers to us, not swallow their tap. The reader-zone sub-label now reads "be the first
— opens the board ↗" in an embed, because it does.

Landing had to be built too, or the link is only half-true: the board now reads `#card=` and
`#post=` and honours them. The first attempt opened the card but not the composer — the composer is
a separate script tag and had not run yet, so a `window.gbCompose` guard was false at that moment.
It now waits for the composer rather than testing for it once. **That half-fix passed a casual look
and was caught only because the suite asserts the composer is open, not that the link exists.**

## Second finding, same run: "nothing is lost" was not true

With no relay deployed, the composer copies the reader's text to their clipboard and says: *"Your
text is copied to your clipboard so nothing is lost."* Tested against all six posting modes:

- the reader's typed prose did survive — but
- **no mode recorded which case or which card the words were about.** A comment written on "The
  voice she says commanded her" came back as a bare paragraph about nothing in particular. For a
  comment, the card is half the meaning.
- **`report` lost its category.** The dropdown — *"It accuses someone who has not been charged"*,
  *"The source does not say what it claims"* — was dropped entirely. That is the moderation-critical
  field, dropped from the one queue EDITORIAL.md tells us to handle before anything else.
- `connection` lost its relation for the same reason.

Cause: the payload is built generically from the mode's own field list, but the clipboard text was
a hardcoded `[claim, url, reasoning, falsify]`. **One list, written in two places** — the fourth
instance of that exact species in this codebase. The clipboard copy is now built from the mode's
own field list, labelled, with a case/card header.

Also fixed while there: `navigator.clipboard.writeText` **rejects**, it does not throw, so the
`try/catch` around it never fired. A failed copy still told the reader their words were safe. The
status line now waits for the write to resolve and says something different if it did not. (Another
call site in the same file already had the `.catch()`; the composer's did not.)
